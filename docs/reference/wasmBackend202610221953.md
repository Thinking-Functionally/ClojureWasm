## Understanding the Existing Architecture

ClojureWasm already has a **dual backend** layout:

```
src/
└── eval/
    ├── backend/
    │   ├── vm.zig          ← bytecode VM (primary, with ARM64/x86_64 JIT)
    │   └── treewalk.zig    ← AST-walking interpreter (simpler, used as reference/fallback)
    ├── compiler.zig        ← Clojure forms → bytecode (feeds vm.zig)
    ├── analyzer.zig        ← semantic analysis of Clojure AST
    └── ...
```

The key insight is that both backends consume the **same analyzed AST** (or the same IR produced by the analyzer/compiler front-end). The bytecode VM has a compiler phase that lowers Clojure forms into a custom bytecode format, and the treewalk interpreter directly walks the AST nodes. This means you already have the clean separation point needed to plug in a third backend.

## What a Wasm Backend Would Mean

There are **two very different things** people mean by "Wasm backend," and the choice fundamentally changes the scope:

### Option A: Compile Clojure to `.wasm` modules (AOT Wasm codegen)

This means adding a `./eval/backend/wasm.zig` that takes the same analyzed Clojure AST and **emits Wasm bytecode** (the binary `.wasm` format) instead of the custom VM bytecode. The output would be a standalone `.wasm` file that runs in any Wasm runtime (browsers, wasmtime, zwasm itself, etc.).

### Option B: Cross-compile the existing VM to `wasm32` (runtime-in-Wasm)

This means using Zig's cross-compilation (`zig build -Dtarget=wasm32-wasi`) to compile the **entire ClojureWasm runtime** — including `vm.zig` and/or `treewalk.zig` — as a Wasm binary. The Clojure code would still be interpreted/VM-executed, but the interpreter itself runs inside Wasm.

Both are valuable. Option B is arguably easier and gets you "Clojure in the browser" quickly. Option A is harder but produces much smaller, faster, more portable output. Let me sketch both.

## Option A: `wasm.zig` — A Wasm Codegen Backend

This is the more ambitious and interesting path. Here's a concrete design:

### 1. The Backend Interface Contract

Looking at how `vm.zig` and `treewalk.zig` are structured, each backend likely implements a common evaluation interface. Your new backend would conform to the same contract:

```zig
// eval/backend/wasm.zig

const std = @import("std");
const ast = @import("../analyzer.zig");        // analyzed Clojure AST
const types = @import("../../types.zig");       // Clojure value types
const wasm_emit = @import("wasm_emit.zig");     // Wasm binary encoder

pub const WasmBackend = struct {
    allocator: std.mem.Allocator,
    module: wasm_emit.Module,
    /// String table for interned symbols / keywords
    string_pool: StringPool,
    /// Function index counter (Wasm function space)
    fn_index: u32 = 0,

    const Self = @This();

    pub fn init(allocator: std.mem.Allocator) Self {
        return .{
            .allocator = allocator,
            .module = wasm_emit.Module.init(allocator),
            .string_pool = StringPool.init(allocator),
        };
    }

    /// Main entry: compile a top-level Clojure form to Wasm
    pub fn compile(self: *Self, form: ast.AnalyzedForm) !void {
        switch (form) {
            .fn_expr   => |f| try self.emitFn(f),
            .invoke    => |i| try self.emitInvoke(i),
            .if_expr   => |c| try self.emitIf(c),
            .let_expr  => |l| try self.emitLet(l),
            .literal   => |v| try self.emitConst(v),
            .var_ref   => |v| try self.emitVarGet(v),
            .do_expr   => |d| try self.emitDo(d),
            .loop_expr => |p| try self.emitLoop(p),
            .recur     => |r| try self.emitRecur(r),
            // ...
        }
    }

    /// Finalize and return the .wasm binary
    pub fn finalize(self: *Self) ![]u8 {
        return self.module.encode(self.allocator);
    }
};
```

### 2. Wasm Binary Emitter

You need a module that writes the actual Wasm binary sections. Since ClojureWasm already depends on **zwasm** (which has a full Wasm decoder/encoder), you could either reuse its encoding infrastructure or write a minimal emitter:

```zig
// eval/backend/wasm_emit.zig

pub const Module = struct {
    types:     std.ArrayList(FuncType),
    funcs:     std.ArrayList(Function),
    memories:  std.ArrayList(Memory),
    globals:   std.ArrayList(Global),
    exports:   std.ArrayList(Export),
    data:      std.ArrayList(DataSegment),
    imports:   std.ArrayList(Import),

    pub fn init(alloc: std.mem.Allocator) Module { ... }

    /// Encode the full module into the Wasm binary format
    pub fn encode(self: *Module, alloc: std.mem.Allocator) ![]u8 {
        var buf = std.ArrayList(u8).init(alloc);
        try buf.appendSlice(&.{ 0x00, 0x61, 0x73, 0x6D }); // magic: \0asm
        try buf.appendSlice(&.{ 0x01, 0x00, 0x00, 0x00 }); // version 1

        try self.encodeTypeSection(&buf);
        try self.encodeImportSection(&buf);
        try self.encodeFunctionSection(&buf);
        try self.encodeMemorySection(&buf);
        try self.encodeGlobalSection(&buf);
        try self.encodeExportSection(&buf);
        try self.encodeCodeSection(&buf);
        try self.encodeDataSection(&buf);

        return buf.toOwnedSlice();
    }
    // ...
};

pub const Function = struct {
    type_idx: u32,
    locals: []ValType,
    body: std.ArrayList(u8),  // raw Wasm bytecodes
};
```

### 3. The Hard Part: Clojure's Value Representation in Wasm

This is where it gets genuinely difficult. Clojure is a dynamically typed language with persistent data structures, closures, garbage collection, and polymorphic dispatch. Wasm's core model is statically typed stack machine with `i32`/`i64`/`f32`/`f64`. You have several options:

**Approach 3a: Boxed values in linear memory (MVP Wasm)**

Everything is an `i32` pointer into linear memory. You implement a GC, a tagged-union value representation, and all persistent data structures in Wasm linear memory. This is essentially what the existing `vm.zig` does, but targeting Wasm opcodes instead of the custom bytecode.

```
Value layout in linear memory:
┌──────────┬──────────────────────┐
│ tag (i32)│ payload (variable)   │
├──────────┼──────────────────────┤
│ 0x01 int │ i64 value            │
│ 0x02 flt │ f64 value            │
│ 0x03 str │ ptr + len            │
│ 0x04 sym │ interned index       │
│ 0x05 kw  │ interned index       │
│ 0x06 vec │ HAMT node ptr        │
│ 0x07 map │ HAMT node ptr        │
│ 0x08 fn  │ code_idx + env_ptr   │
│ ...      │                      │
└──────────┴──────────────────────┘
```

**Approach 3b: WasmGC (struct/array/ref types)**

With WasmGC (now ratified in Wasm 3.0, which zwasm already supports), you can use `struct` and `array` types with the host GC. This is much cleaner — no manual memory management — but limits you to runtimes that support the GC proposal.

```wasm
;; WasmGC-style value representation
(type $Value (struct
  (field $tag i32)
  (field $data (ref any))))

(type $Closure (struct
  (field $func_idx i32)
  (field $env (ref $ValueArray))))

(type $ValueArray (array (mut (ref $Value))))
```

### 4. Mapping Clojure Constructs to Wasm

Here's how the core forms would lower:

| Clojure Form | Wasm Strategy |
|---|---|
| `(def x 42)` | Global `i32` slot → module global or memory offset |
| `(fn [a b] ...)` | Wasm function + closure environment struct |
| `(if test then else)` | `if/else/end` block |
| `(let [x 1] ...)` | Local variables (`local.set` / `local.get`) |
| `(loop/recur)` | Wasm `loop/br` (maps beautifully) |
| `(+ a b)` | Inline as `i64.add` (when type-inferred), otherwise runtime dispatch |
| `(map f coll)` | Call into runtime library (imported or inlined) |
| `(.method obj)` | N/A — no host interop in pure Wasm (use imports) |

## Option B: Cross-compile the Runtime to `wasm32-wasi`

This is the pragmatic first step. Zig already cross-compiles to `wasm32-wasi`:

```bash
zig build -Dtarget=wasm32-wasi -Doptimize=ReleaseSmall
# produces cljw.wasm — the entire runtime as a WASI module
```

Then you'd run it with:
```bash
zwasm run cljw.wasm -- -e '(+ 1 2)'
# or in Node.js, Deno, browser with WASI polyfill, etc.
```

The challenges here are more mechanical: the Zig source likely uses OS-specific things (file I/O, mmap for the JIT, signal handlers) that need `wasm32-wasi` shims or conditional compilation. The JIT backend obviously can't work inside Wasm, so you'd fall back to the treewalk or pure-interpreter VM mode. This is exactly why having the treewalk backend is valuable — it's portable and has no platform-specific code generation.

## Recommended Roadmap

Here's the order I'd suggest:

**Phase 1 — Cross-compile treewalk to `wasm32-wasi`** (weeks, not months). Gate off the JIT, disable mmap, use the treewalk backend. You get "Clojure in the browser" immediately. This validates the runtime's portability.

**Phase 2 — Cross-compile the bytecode VM (interpreter-only mode) to `wasm32-wasi`** (slightly harder). The VM without JIT is still faster than treewalk and should be portable. The bytecode dispatch loop maps well to Wasm's structured control flow.

**Phase 3 — Standalone `wasm.zig` codegen backend** (months of work). This is the "compile Clojure to .wasm" path. Start with a subset: numeric functions with `loop/recur`, no closures, no persistent data structures. Get `(defn fib [n] ...)` compiling to a standalone `.wasm`. Then incrementally add closures, persistent vectors, maps, etc.

**Phase 4 — WasmGC backend** (research-grade). Use WasmGC's struct/array/ref types for the value representation. This eliminates the need for a manual GC in linear memory and is the "correct" long-term approach for a dynamic language targeting Wasm.

---

The existing dual-backend architecture in ClojureWasm makes this much more tractable than it would be in a monolithic interpreter — the analyzed AST is already the clean hand-off point, and `vm.zig` already demonstrates how to lower Clojure semantics into a lower-level instruction set. Wasm bytecode is just a different instruction set with stricter typing. The hard part isn't the backend plumbing; it's the value representation and runtime library (GC, persistent data structures, `Var` dispatch) in a Wasm-native way.

### 3.1 The Compilation Pipeline

The pipeline from Clojure source to `.wasm` has these stages:

```
  source.clj
      │
      ▼
 ┌──────────┐
 │  Reader   │   ← reads text into Clojure data (forms)
 └────┬─────┘
      │  raw AST (lists, symbols, vectors...)
```

The analyzer is **shared** with the existing VM and treewalk backends. You only write the last two boxes.

### 3.2 Value Representation in Linear Memory

This is the single most consequential design decision. Every Clojure value — numbers, strings, keywords, vectors, maps, functions — must be represented as bytes in Wasm linear memory, and every operation must know how to read the tag, dispatch on type, and manipulate the payload.

Here's a concrete layout using NaN-boxing (packing type tags into the unused bits of IEEE 754 NaN values):

```
NaN-boxing scheme (64-bit):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 Bit 63    62-52        51          50-48       47-0
 ┌─────┬────────────┬───────┬───────────────┬──────────────────┐
 │sign │ exponent   │ quiet │  tag (3 bits) │ payload (48 bit) │
 │  1  │  11 bits   │  NaN  │               │                  │
 └─────┴────────────┴───────┴───────────────┴──────────────────┘

If exponent is NOT all-1s → it's a plain f64 (doubles pass through)
If exponent IS all-1s and quiet=1 → tagged pointer / immediate:

  tag=000  →  pointer to heap object (48-bit address space)
  tag=001  →  integer (small fixnum, 48-bit signed)
  tag=010  →  boolean (payload: 0=false, 1=true)
  tag=011  →  nil (payload ignored)
  tag=100  →  symbol (interned index)
  tag=101  →  keyword (interned index)
  tag=110  →  char (Unicode codepoint)
  tag=111  →  reserved
```

The advantage of NaN-boxing is that every Clojure value fits in a single `i64` Wasm local or stack slot. No indirection for numbers. Heap objects (strings, vectors, maps, closures) are accessed through the 48-bit pointer.

An alternative is a simpler **tagged-pointer** scheme where everything is an `i32` pointer and integers/floats are always boxed. Simpler to implement, slower for arithmetic.

Here's what heap objects look like in linear memory:

```
Heap object header (at the pointer address):
┌────────────────┬────────────────┬──────────────────────┐
│ GC mark (i32)  │ obj_type (i32) │ payload...           │
├────────────────┼────────────────┼──────────────────────┤
│ 0 or 1         │ OBJ_STRING     │ len(i32), utf8 bytes │
│                │ OBJ_VEC        │ count, shift, root   │
│                │ OBJ_MAP        │ count, root_node     │
│                │ OBJ_CLOSURE    │ fn_idx, env_ptr, ... │
│                │ OBJ_CONS       │ first_ptr, rest_ptr  │
│                │ OBJ_BIGINT     │ sign, limbs...       │
│                │ OBJ_ATOM       │ value_ptr            │
└────────────────┴────────────────┴──────────────────────┘
```

### 3.3 Memory Allocator and Garbage Collector

You need a GC that runs entirely inside Wasm linear memory. The standard approach is a **mark-and-sweep** collector, since it's the simplest to implement correctly in a constrained environment.

```
Linear memory layout:
┌─────────────────┬──────────────────────┬───────────────┐
│ Static data     │ Heap (GC-managed)    │ Stack shadow  │
│ (string pool,   │                      │ (for GC roots │
│  global vars)   │                      │  scanning)    │
├─────────────────┼──────────────────────┼───────────────┤
│ 0x0000─0x0FFF   │ 0x1000─(grows →)     │ (← grows)    │
└─────────────────┴──────────────────────┴───────────────┘
```

The GC needs to know where **roots** are. Roots are Wasm locals and globals that hold Clojure values. Since Wasm doesn't let you introspect the operand stack or local variables at runtime, you maintain a **shadow stack** — a region of linear memory where the compiler explicitly spills live references before any allocation that might trigger GC:

```zig
// During Wasm codegen, before emitting an allocation:
fn emitAlloc(self: *WasmBackend, size: u32, live_refs: []LocalIdx) !void {
    // 1. Push all live references onto the shadow stack
    for (live_refs) |ref| {
        try self.emit(.local_get, ref);
        try self.emitCall(self.rt.shadow_stack_push);
    }

    // 2. Call the allocator (which may trigger GC)
    try self.emitI32Const(size);
    try self.emitCall(self.rt.gc_alloc);

    // 3. Pop references back (GC may have moved them if compacting)
    var i = live_refs.len;
    while (i > 0) {
        i -= 1;
        try self.emitCall(self.rt.shadow_stack_pop);
        try self.emit(.local_set, live_refs[i]);
    }
}
```

The mark phase walks from roots (shadow stack + globals), following all pointers in heap objects. The sweep phase builds a free list from unmarked objects. A **compacting** collector is better for Wasm (reduces fragmentation, improves memory locality) but significantly harder to implement because you must update all pointers.

### 3.4 Persistent Data Structures

Clojure's immutable vectors and hash maps are based on **Hash Array Mapped Tries (HAMT)**. You implement these as tree structures in linear memory.

A persistent vector with branching factor 32:

```
PersistentVector in linear memory:

┌─────────────────────────────────┐
│ VEC header                      │
│  count: i32                     │
│  shift: i32  (depth × 5)       │
│  root:  i32  (ptr to root node)│
│  tail:  i32  (ptr to tail arr) │
└──────────┬──────────────────────┘
           │
           ▼
    ┌─────────────────────┐
    │ Node (32 slots)     │
    │ [0]: ptr to child   │──→ ...
    │ [1]: ptr to child   │──→ ...
    │ ...                 │
    │ [31]: ptr to child  │──→ leaf values
    └─────────────────────┘
```

When you `conj` an element, you **path-copy** from root to the insertion point, sharing all unchanged subtrees. In Wasm, this means allocating a few new 32-slot node arrays and copying pointers.

The critical operations and their approximate Wasm instruction counts:

```
nth(vec, i):    ~3 levels of i32.load + shift/mask → ~20 instructions
conj(vec, v):   tail-insert or path-copy           → ~100-200 instructions
assoc(vec,i,v): path-copy from root to leaf         → ~80-150 instructions
```

For hash maps, you implement a HAMT with bitmap-indexed nodes (compressed sparse arrays). Each node stores a 32-bit bitmap indicating which of the 32 hash-fragment slots are occupied, plus a compact array of only the occupied entries. This is more complex but memory-efficient.

### 3.5 Compiling Clojure Forms to Wasm Instructions

Let me walk through each major form and show the concrete Wasm instructions generated.

**Literals:**

```clojure
42
```
```wasm
;; NaN-boxed integer: set tag=001 in NaN bits, payload=42
i64.const 0x7FF1_0000_0000_002A  ;; precomputed NaN-boxed 42
```

**Arithmetic with type specialization:**

```clojure
(+ a b)
```

If the analyzer can prove `a` and `b` are both integers (via type inference or hints), emit the fast path:

```wasm
;; Fast path: both are fixnums
local.get $a
i64.const 0x0000FFFFFFFFFFFF   ;; mask out tag bits, keep 48-bit payload
i64.and
local.get $b
i64.const 0x0000FFFFFFFFFFFF
i64.and
i64.add
;; Re-tag as integer
i64.const 0x7FF1000000000000
i64.or
```

Without type information, you must emit a **dispatch**:

```wasm
;; Slow path: runtime type dispatch
local.get $a
local.get $b
call $clj_add       ;; runtime function that checks tags and dispatches
```

**`if` expressions:**

```clojure
(if test then-expr else-expr)
```
```wasm
;; Evaluate test
<compile test>
;; Check truthiness: not nil and not false
call $is_truthy        ;; returns i32 (0 or 1)
if (result i64)        ;; Wasm structured if, result is a Clojure value
  <compile then-expr>
else
  <compile else-expr>
end
```

**`let` bindings:**

```clojure
(let [x 1 y (+ x 2)] y)
```
```wasm
;; x = 1
i64.const <nan-boxed 1>
local.set $x

;; y = (+ x 2)
local.get $x
i64.const <nan-boxed 2>
call $clj_add
local.set $y

;; body: y
local.get $y
```

Each `let` binding maps to a Wasm `local`. The compiler maintains a scope map from Clojure symbols to Wasm local indices.

**`fn` (closures):**

This is where things get interesting. A Clojure function that closes over variables needs a **closure object**: a pair of (function index, captured environment).

```clojure
(let [x 10]
  (fn [y] (+ x y)))
```

The compiler emits two things. First, a top-level Wasm function for the body:

```wasm
;; Function $fn_7 (the lambda body)
;; param 0: closure env pointer (i32)
;; param 1: y (i64, Clojure value)
;; result: i64 (Clojure value)
(func $fn_7 (param $env i32) (param $y i64) (result i64)
  ;; Load captured x from closure environment
  local.get $env
  i32.load offset=0        ;; first captured value
  ;; Now stack has: x (as i64... need to load i64 from that memory)
  ;; ... (actual encoding depends on env layout)

  local.get $y
  call $clj_add
)
```

Second, at the point where the `fn` form is evaluated, it allocates a closure object:

```wasm
;; Allocate closure: {fn_idx: 7, env: [x]}
i32.const 12              ;; size: 4 (fn_idx) + 4 (env_len) + 4 (one captured val ptr)
call $gc_alloc
local.tee $closure_ptr

;; Store fn_idx
i32.const 7
i32.store offset=0

;; Store env length
i32.const 1
i32.store offset=4

;; Store captured x
local.get $closure_ptr
local.get $x
i64.store offset=8

local.get $closure_ptr
;; NaN-box as heap pointer with tag=000
;; ... tag it as a closure value
```

**Function invocation** then looks up the closure, extracts the function index, and does an `call_indirect` through the Wasm table:

```clojure
(f 42)
```
```wasm
;; Extract fn_idx from closure
local.get $f
call $unwrap_closure_ptr  ;; strips NaN-box tag → i32 heap ptr
local.tee $cptr
i32.load offset=0         ;; fn_idx → i32

;; Push closure env as first arg
local.get $cptr

;; Push actual argument
i64.const <nan-boxed 42>

;; Indirect call through function table
call_indirect (type $fn_1_arg)   ;; type: (i32, i64) → i64
```

The `call_indirect` instruction uses a Wasm **table** — an array of function references indexed by integer. Every compiled Clojure function gets a slot in this table.

**`loop` / `recur`:**

This maps beautifully to Wasm's structured control flow:

```clojure
(loop [i 0 acc 1]
  (if (= i n)
    acc
    (recur (inc i) (* acc i))))
```
```wasm
;; Initialize loop bindings
i64.const <nan-boxed 0>
local.set $i
i64.const <nan-boxed 1>
local.set $acc

;; Wasm loop
(loop $loop_0
  ;; (= i n)
  local.get $i
  local.get $n
  call $clj_eq
  call $is_truthy
  (if (result i64)
    (then
      local.get $acc              ;; return acc
    )
    (else
      ;; Compute new bindings
      local.get $i
      call $clj_inc
      local.set $i_new

      local.get $acc
      local.get $i
      call $clj_mul
      local.set $acc_new

      ;; Rebind
      local.get $i_new
      local.set $i
      local.get $acc_new
      local.set $acc

      ;; Branch back to loop head
      br $loop_0
      ;; Unreachable, but Wasm needs a value for the block type
      i64.const 0
    )
  )
)
```

### 3.6 The Runtime Library

A large portion of Phase 3 is implementing the **runtime library** — a set of Wasm functions that provide core Clojure operations. These are compiled alongside the user code into the same `.wasm` module (or imported from a separate runtime module).

The runtime includes: `clj_add`, `clj_sub`, `clj_mul`, `clj_div` (polymorphic arithmetic); `clj_eq`, `clj_lt`, `clj_gt` (polymorphic comparison); `clj_conj`, `clj_assoc`, `clj_nth`, `clj_get` (persistent data structure operations); `clj_first`, `clj_rest`, `clj_seq`, `clj_cons` (sequence operations); `clj_str`, `clj_pr_str`, `clj_println` (string/IO operations); `gc_alloc`, `gc_collect` (memory management); `is_truthy`, `unwrap_closure_ptr`, `type_tag` (value utilities).

You can write this runtime in Zig and compile it to Wasm separately, then link it with user code. Or you can emit it directly as Wasm bytecodes from `wasm.zig`. The Zig-to-Wasm approach is more maintainable:

```zig
// runtime/clj_core.zig — compiled to wasm32-wasi or wasm32-freestanding

export fn clj_add(a: u64, b: u64) u64 {
    const tag_a = extractTag(a);
    const tag_b = extractTag(b);

    if (tag_a == TAG_INT and tag_b == TAG_INT) {
        const va = extractFixnum(a);
        const vb = extractFixnum(b);
        return boxFixnum(va + vb);
    }
    if (tag_a == TAG_FLOAT or tag_b == TAG_FLOAT) {
        const fa = toFloat(a);
        const fb = toFloat(b);
        return @bitCast(u64, fa + fb); // plain f64, NaN-boxing passes through
    }
    // BigInt, Ratio, etc.
    @panic("unsupported operand types for +");
}
```

### 3.7 Host Interop via Wasm Imports/Exports

The `.wasm` module can't do I/O by itself. You expose the outside world through Wasm imports:

```wasm
(import "host" "print_str" (func $host_print (param i32 i32)))  ;; ptr, len
(import "host" "read_file"  (func $host_read  (param i32 i32) (result i32)))
(import "host" "time_ms"    (func $host_time  (result i64)))
```

The host environment (browser JS, wasmtime, zwasm) provides these imports. This is how `println`, file I/O, and any external interaction works.

### 3.8 Incremental Build Strategy

You don't build all of this at once. The recommended order within Phase 3:

**3.8a — Numeric subset** (2-4 weeks). Support only `i64` integers and `f64` floats. No heap allocation. Compile `defn` with simple arithmetic, `if`, `let`, `loop/recur`. Get `(defn fib [n] ...)` producing a valid `.wasm` that runs in wasmtime.

**3.8b — Strings and basic heap** (2-3 weeks). Add a bump allocator (no GC yet). Support strings, `str`, `println`. This forces you to design the heap layout and host import story.

**3.8c — Closures** (2-3 weeks). Add closure allocation, `call_indirect` dispatch, captured environments. This unlocks higher-order functions.

**3.8d — Persistent vectors** (3-4 weeks). Implement the 32-way HAMT in linear memory. Add `vector`, `conj`, `nth`, `assoc`, `count`. Now you need a real GC (mark-and-sweep) because data structures create garbage.

**3.8e — Persistent maps, keywords, symbols** (3-4 weeks). HAMT maps with bitmap-indexed nodes, interned keywords/symbols, `get`, `assoc`, `dissoc`, `keys`, `vals`.

**3.8f — Sequences and laziness** (4-6 weeks). `lazy-seq`, `map`, `filter`, `reduce`, `take`, `drop`. Lazy sequences are thunks (closures that are called on first access and memoize their result). This is challenging because it combines closures with mutation (the thunk cache).

**3.8g — Var system and namespaces** (2-3 weeks). `def`, `defn`, dynamic vars, `binding`. Vars are global mutable slots with metadata. Namespaces are maps from symbols to vars.

**3.8h — Protocols and multimethods** (4-6 weeks). Protocol dispatch requires looking up the type of the first argument and finding the correct implementation. In Wasm, this is a table lookup: type tag → function index in the protocol's dispatch table.

This timeline totals roughly 6-9 months of focused work for a single developer.

## Phase 4: WasmGC Backend

Phase 4 is a fundamentally different approach. Instead of managing memory yourself in linear memory, you use the **WasmGC proposal** (now part of the Wasm standard as of late 2023, supported in Chrome, Firefox, and other V8/SpiderMonkey-based runtimes). WasmGC adds struct types, array types, reference types, and host-managed garbage collection to Wasm.

### 4.1 Why WasmGC Changes Everything

In Phase 3, you spent a huge effort on: a custom GC in linear memory, a shadow stack for root tracking, manual pointer tagging (NaN-boxing), and manual heap layout for every data type. WasmGC eliminates all of that. The host runtime (browser, wasmtime) provides the GC, and you define your data types as **Wasm struct/array types** that the host knows how to trace and collect.

The tradeoff: WasmGC limits where your output can run. As of early 2025, WasmGC is supported in V8 (Chrome, Node, Deno), SpiderMonkey (Firefox), and wasm-tools. It's not yet in wasmtime's default configuration, and WASI support is evolving. By contrast, Phase 3's linear-memory approach runs everywhere.

### 4.2 WasmGC Type Definitions for Clojure Values

WasmGC lets you define nominal struct and array types. Here's how you'd model Clojure's value system:

```wasm
;; ─── Base value type ───
;; We use a single top-level struct with a tag, then downcast.
(type $Value (sub (struct
  (field $tag i32)
)))

;; ─── Numeric types ───
(type $Int (sub $Value (struct
  (field $tag i32)        ;; = TAG_INT
  (field $val i64)
)))

(type $Float (sub $Value (struct
  (field $tag i32)        ;; = TAG_FLOAT
  (field $val f64)
)))

;; ─── String ───
(type $String (sub $Value (struct
  (field $tag i32)        ;; = TAG_STRING
  (field $data (ref $I8Array))
)))
(type $I8Array (array (mut i8)))

;; ─── Keyword / Symbol ───
(type $Keyword (sub $Value (struct
  (field $tag i32)
  (field $ns  (ref null $String))
  (field $name (ref $String))
  (field $hash i32)           ;; cached hash
)))

;; ─── Persistent Vector ───
(type $PVec (sub $Value (struct
  (field $tag   i32)           ;; = TAG_VEC
  (field $count i32)
  (field $shift i32)
  (field $root  (ref null $VNode))
  (field $tail  (ref $ValueArray))
)))

(type $VNode (struct
  (field $children (ref $NodeArray))
))
(type $NodeArray  (array (mut (ref null $VNode))))
(type $ValueArray (array (mut (ref null $Value))))

;; ─── Persistent HashMap ───
(type $PMap (sub $Value (struct
  (field $tag   i32)           ;; = TAG_MAP
  (field $count i32)
  (field $root  (ref null $HNode))
)))

(type $HNode (struct
  (field $bitmap i32)
  (field $entries (ref $EntryArray))
))
(type $MapEntry (struct
  (field $key   (ref $Value))
  (field $val   (ref $Value))
))
(type $EntryArray (array (mut (ref null $Value))))
;; entries array interleaves keys and values, or child nodes

;; ─── Closure ───
(type $Closure (sub $Value (struct
  (field $tag    i32)          ;; = TAG_FN
  (field $fn_idx i32)          ;; index into funcref table
  (field $arity  i32)
  (field $env    (ref null $ValueArray))   ;; captured bindings
)))

;; ─── Cons / LazySeq ───
(type $Cons (sub $Value (struct
  (field $tag   i32)
  (field $first (ref null $Value))
  (field $rest  (ref null $Value))
)))

(type $LazySeq (sub $Value (struct
  (field $tag      i32)
  (field $thunk    (ref null $Closure))   ;; fn to call on first access
  (field $realized (mut i32))              ;; 0 or 1
  (field $cached   (mut (ref null $Value)))
)))
```

The key difference from Phase 3: **all of these are GC-managed references**. You never call `gc_alloc` or `gc_collect`. You just use `struct.new` and the host GC handles the rest.

### 4.3 Creating and Accessing Values

Creating a value is a single instruction:

```wasm
;; Create an integer value
i32.const 1            ;; TAG_INT
i64.const 42
struct.new $Int        ;; → (ref $Int) on the stack
```

Accessing a field:

```wasm
;; Get the i64 payload from an Int
local.get $val         ;; (ref $Value)
ref.cast $Int          ;; downcast, traps if wrong type → (ref $Int)
struct.get $Int $val   ;; → i64 on the stack
```

The `ref.cast` instruction performs a runtime type check and traps (throws) if the value isn't actually an `$Int`. This replaces the manual tag checking in Phase 3.

### 4.4 How Compilation Differs from Phase 3

The Wasm instructions you emit are structurally similar but use GC instructions instead of linear memory loads/stores. Here's the comparison for a few key operations:

**Creating a vector `[1 2 3]`:**

Phase 3 (linear memory):
```wasm
i32.const 48           ;; alloc 48 bytes for tail array
call $gc_alloc         ;; → i32 pointer
local.tee $tail
;; store element 0
i64.const <nan-boxed 1>
i64.store offset=0
;; store element 1...
;; ... then allocate VEC header, store count/shift/root/tail...
```

Phase 4 (WasmGC):
```wasm
;; Create tail array with 3 elements
i32.const 3
array.new_default $ValueArray    ;; → (ref $ValueArray)
local.tee $tail

;; Set elements
i32.const 0
i32.const 1                      ;; TAG_INT
i64.const 1
struct.new $Int                  ;; → (ref $Int)
array.set $ValueArray            ;; tail[0] = Int(1)

;; ... repeat for elements 1, 2 ...

;; Create the PVec struct
i32.const 5                      ;; TAG_VEC
i32.const 3                      ;; count
i32.const 5                      ;; shift
ref.null $VNode                  ;; root (null for small vecs)
local.get $tail
struct.new $PVec                 ;; → (ref $PVec), done!
```

No manual memory layout, no pointer arithmetic, no GC shadow stack. The host runtime traces all `ref` fields automatically.

**Closure creation:**

Phase 3:
```wasm
i32.const 20                     ;; alloc closure struct
call $gc_alloc
local.tee $cptr
i32.const 7                      ;; fn_idx
i32.store offset=0
i32.const 1                      ;; env length
i32.store offset=4
local.get $cptr
local.get $captured_x
i64.store offset=8               ;; captured value
;; NaN-box the pointer...
```

Phase 4:
```wasm
;; Build captured env array
i32.const 1
array.new_default $ValueArray
local.tee $env
i32.const 0
local.get $captured_x
array.set $ValueArray

;; Build closure struct
i32.const 8                      ;; TAG_FN
i32.const 7                      ;; fn_idx
i32.const 1                      ;; arity
local.get $env
struct.new $Closure              ;; done
```

### 4.5 Polymorphic Dispatch with WasmGC

When you call `(+ a b)` and don't know the types, you need runtime dispatch. With WasmGC, you can use `ref.test` (a non-trapping type test) instead of manual tag inspection:

```wasm
(func $clj_add (param $a (ref $Value)) (param $b (ref $Value)) (result (ref $Value))
  ;; Try: both are Int
  (block $not_both_int
    local.get $a
    ref.test $Int
    i32.eqz
    br_if $not_both_int

    local.get $b
    ref.test $Int
    i32.eqz
    br_if $not_both_int

    ;; Fast path: int + int
    local.get $a
    ref.cast $Int
    struct.get $Int $val

    local.get $b
    ref.cast $Int
    struct.get $Int $val

    i64.add

    ;; Box result
    i32.const 1
    local.get $result     ;; the i64 sum
    struct.new $Int
    return
  )

  ;; Try: either is Float → promote to float addition
  (block $not_float
    ;; ... similar pattern with ref.test $Float ...
  )

  ;; Fallback: BigInt, Ratio, etc.
  unreachable
)
```

This is conceptually similar to Phase 3's tag dispatch, but instead of bit-masking an i64, you use the host's type system. The host JIT compiler (V8's TurboFan, SpiderMonkey's IonMonkey) can optimize these type checks far better than it can optimize manual tag extraction in linear memory.

### 4.6 Protocol Dispatch with WasmGC

Clojure protocols are the most interesting dispatch mechanism. With WasmGC, you can model protocols as **interface types** using the subtyping hierarchy, or more practically, as dispatch tables keyed by the type tag.

The dispatch table approach:

```wasm
;; Protocol ISeq: first, rest, cons
;; Each type that implements ISeq registers its implementations

;; Dispatch table: indexed by type tag
(type $ProtocolTable (array (mut (ref null $Closure))))

;; Global dispatch table for ISeq.first
(global $iseq_first_table (mut (ref $ProtocolTable))
  i32.const 16                              ;; 16 type tags
  array.new_default $ProtocolTable
)

;; At init time, register implementations:
;; For Cons type (tag=10):
(func $init_protocols
  global.get $iseq_first_table
  i32.const 10                               ;; TAG_CONS
  ;; create a closure wrapping $cons_first
  ...
  array.set $ProtocolTable
)

;; Dispatch:
(func $iseq_first (param $obj (ref $Value)) (result (ref $Value))
  global.get $iseq_first_table
  local.get $obj
  struct.get $Value $tag                     ;; get type tag
  array.get $ProtocolTable                   ;; look up implementation
  ;; ... call it via call_ref ...
)
```

An alternative approach using WasmGC's type hierarchy would define `$ISeq` as a supertype and have `$Cons`, `$LazySeq`, etc. be subtypes. Then dispatch uses `ref.cast`. However, Clojure protocols can be extended to existing types after the fact (`extend-protocol`), which makes the table approach more flexible.

### 4.7 The `call_ref` Advantage

WasmGC also comes with the **typed function references** proposal. Instead of `call_indirect` with an integer table index, you can store a `(ref $func_type)` directly in a struct and call it with `call_ref`:

```wasm
(type $Fn1 (func (param (ref $Value)) (result (ref $Value))))

;; In a closure struct:
(type $Closure_v2 (struct
  (field $code (ref $Fn1))           ;; direct function reference!
  (field $env  (ref null $ValueArray))
))

;; Invocation — no table lookup needed:
local.get $closure
struct.get $Closure_v2 $code
local.get $arg
call_ref $Fn1
```

This is faster than Phase 3's `call_indirect` because the host JIT can potentially inline through `call_ref` in hot paths, and it avoids the table bounds check.

### 4.8 What You No Longer Need to Build

Compared to Phase 3, an entire category of complex infrastructure disappears:

Phase 3 had several components that Phase 4 eliminates entirely. The garbage collector (mark-and-sweep, root scanning, shadow stack) is replaced by the host GC. The memory allocator (free lists, compaction) is replaced by `struct.new` and `array.new`. NaN-boxing or pointer tagging is replaced by WasmGC reference types and `ref.cast`. Manual heap layout (computing offsets, alignment) is replaced by `struct.get`/`struct.set`. The shadow stack for GC roots is completely unnecessary since the host traces Wasm locals automatically.

This is a **massive reduction in implementation complexity**. The runtime library shrinks dramatically. Your compiler is simpler because it doesn't need to emit allocation boilerplate or worry about which locals are live across GC points.

### 4.9 What's Harder in Phase 4

It's not all easier. There are a few things that are trickier with WasmGC.

**Interop with linear memory:** If you need to call C libraries or do raw byte manipulation (parsing, binary protocols), you still need linear memory. WasmGC structs and linear memory are separate address spaces. You need explicit copying between them.

**Runtime flexibility:** In Phase 3, you can do anything — reinterpret memory, build custom allocators, implement tagged unions however you want. WasmGC's type system is more rigid. For example, you can't have a union type that's "either an Int or a pointer to a VNode" without wrapping both in a common supertype.

**Tooling maturity:** WasmGC is newer. Debugging tools, profilers, and benchmarking infrastructure are less mature. Some Wasm runtimes have incomplete or unoptimized WasmGC support.

**Binary size:** WasmGC modules tend to be larger because of the type section (every struct and array type needs a full type definition). Phase 3's linear memory approach has a tiny type section.

### 4.10 Phase 4 Build Strategy

**4.10a — Port the type system** (2-3 weeks). Define all the WasmGC types above. Write a test that creates and reads back values. Verify in Chrome DevTools or wasm-tools validate.

**4.10b — Port arithmetic and control flow** (2-3 weeks). `+`, `-`, `*`, `/`, `if`, `let`, `loop/recur`. The compiler changes are mostly mechanical — swap `i64.store`/`i64.load` for `struct.new`/`struct.get`.

**4.10c — Port closures** (1-2 weeks). Easier than Phase 3 because `struct.new $Closure` is trivial compared to manual heap layout.

**4.10d — Port persistent data structures** (3-4 weeks). Rewrite HAMT using `array.new`/`array.get`/`array.set` and `struct.new`/`struct.get`. The algorithms are identical to Phase 3; only the memory operations change.

**4.10e — Port sequences and lazy evaluation** (2-3 weeks). `LazySeq` is a struct with a mutable `$realized` field and a mutable `$cached` ref. `struct.set` handles the mutation.

**4.10f — Benchmark against Phase 3** (ongoing). The key question: does the host GC outperform your custom mark-and-sweep? For most workloads, yes — V8's Orinoco GC is generational, concurrent, and heavily optimized. Your Phase 3 GC is a simple stop-the-world collector.

This timeline is roughly 3-4 months, significantly shorter than Phase 3, because you're reusing all the algorithmic work (HAMT, sequence abstractions, protocol dispatch logic) and only changing the memory layer.

## Summary: Phase 3 vs Phase 4 Decision Matrix

Phase 3 (Linear Memory) is the right choice when you need maximum portability across all Wasm runtimes (including embedded/IoT), when you need fine-grained control over memory layout and GC behavior, when your target is WASI-based server-side execution (wasmtime, wasmer), and when you want zero dependency on bleeding-edge Wasm proposals.

Phase 4 (WasmGC) is the right choice when your primary target is browsers (V8, SpiderMonkey), when you want to minimize implementation effort and maintenance burden, when you want the best possible runtime performance (host JIT + host GC), and when you're building something that interacts with the JS/DOM ecosystem.

The pragmatic path: build Phase 3 first for the core subset, then start Phase 4 in parallel once you have a working test suite and benchmark harness. The two backends share the front-end (reader, analyzer) and the algorithmic core (HAMT implementations, sequence protocols) — only the codegen layer differs. Having both backends also lets you validate correctness by cross-checking their outputs.
